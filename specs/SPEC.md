# Multi-Line Hero SPEC

## 1. Product Summary

Multi-Line Hero is a multiplayer-first browser arena survival game. Each player controls a hero in a private fixed arena while server-authored creep waves enter from outside the arena edges and converge on the hero. Players survive, collect weapons, and indirectly pressure nearby matched players through future creep-wave systems.

## 2. Core Goals

- Run as a Vite TypeScript client with Bun for all tooling and the local server runtime.
- Render the arena and combat on a full-window responsive canvas.
- Use stable HTML overlays for joining, player status, neighbors, wave notices, and inventory.
- Run a Bun TypeScript server serving the built client and gameplay WebSockets at `/ws`.
- Keep account and character identity, password authentication, single-session presence, score, wave turns, and neighbor links authoritative on the server and persist player records through Bun SQL. Passwords are stored only as Bun password hashes, never as plaintext. An account may own multiple named characters. Each character has independent progression, equipment, score, and wave state, while every character on the account uses the same backpack inventory as a shared stash.
- Share WebSocket message types through `common/protocol.ts`.
- Keep mechanics in `specs/MECHANICS_SPEC.md` and progression/item/build rules in `specs/PROGRESSION_SPEC.md`.

## 3. Specification Boundaries

- `specs/SPEC.md` is authoritative for product goals, runtime architecture, server ownership, multiplayer/economy boundaries, UX direction, WebSocket protocol, and development process.
- `specs/MECHANICS_SPEC.md` is authoritative for arena simulation, movement, targeting, attack telegraphs, projectiles, collision resolution, damage sources, and local defeat reset.
- `specs/PROGRESSION_SPEC.md` is authoritative for permanent XP, attributes, derived stats, item generation, equipment, shared skill rules, generated enemy builds, drops, wave composition, and rival scaling. `specs/spells/` contains the authoritative per-spell contracts; `specs/item-effects/` contains the authoritative contracts for item-applied slow effects.

## 4. Hero and Combat Summary

- Every joined player controls one hero in a private fixed arena, initially placed at the arena center.
- The hero has health instead of lane lives.
- Enemy body contact does not damage the hero; see `specs/MECHANICS_SPEC.md` for damage sources and attack resolution.
- A newly created player is empty-handed and receives exactly three randomly generated level-0 Common equipment items in the backpack. This starter roll happens only once at account creation; defeat neither grants nor rerolls starter equipment. Existing saved players keep their current equipment when this default changes. Plain Clubs remain valid legacy and generated equipment, but the game never creates one as an equipment fallback.
- Generated enemy weapons can drop into the arena and be collected into the backpack. Weapon classes, requirements, affixes, skills, and progression follow `specs/PROGRESSION_SPEC.md`.
- Hero auto-aim, automatic attacks, attack areas, projectiles, and dodge rules follow `specs/MECHANICS_SPEC.md`.
- Active weapon and learned skill availability, costs, and scaling follow `specs/PROGRESSION_SPEC.md`.
- Particle effects remain future work.

## 5. Creep and Wave Rules

- The server advances a numbered wave turn for each connected player and sends one `incomingWave` payload per turn.
- The client only spawns creeps described by server-authored waves and staggers them using the supplied interval. Browser focus loss or a delayed frame never releases a backlog together: at most one due creep is released per fixed update, preserving the authored spawn debounce while catching up. At most 100 living creeps may be active in an arena at once. Due spawns beyond that cap remain in the FIFO wave queue, even as later waves arrive, and resume at the normal one-per-fixed-update cadence when defeats open slots; queued creeps are never discarded.
- Early waves contain melee creeps. Beginning with wave 3, waves also contain ranged bubble shooters, with their presence increasing later.
- Creep spawn positioning, steering, melee telegraphs, ranged projectiles, and collision behavior follow `specs/MECHANICS_SPEC.md`.
- Wave size, spawn batching, generated enemy builds, XP, drops, and rival scaling follow `specs/PROGRESSION_SPEC.md`.
- Killing a creep awards its bounty locally and its score value through the server.
- A creep no longer leaks or exits through a lane.
- Defeat is reported to the server. Before resetting the player's authoritative wave number to 1, the server retains the highest non-Training wave that hero has reached as a permanent profile best, then sends the adjusted wave number back to the client and neighbor summaries. The profile best never decreases across defeats.
- After the local defeat reset finishes, the client requests a replacement wave. The server sends a fresh wave-1 `incomingWave` with the normal preparation delay; this replacement request must not increment the wave number again. Any automatic rematch or later explicit Enter Realm after that death also begins at wave 1.

## 6. Multiplayer and Economy

- Players start in the Halls of Realms lobby and must explicitly choose Enter Realm before matchmaking. Connected, opted-in players are placed in stable server-owned 1v1, 1v2, or 1v3 realm groups until disconnect, voluntary exit, or realm defeat.
- The Training Grounds header offers two explicit realm starts: `Enter wave N`, where N is the hero's persisted best wave (with a minimum of 1), and `Enter wave 1`. Either starts play immediately at the selected wave even when no opponent is available. When the browser-local `Fullscreen on game start` setting is On, either button gesture requests browser fullscreen for the complete game document before matchmaking begins; the setting defaults to On, and denial or lack of fullscreen support never blocks realm entry. When the setting is Off, realm entry does not request fullscreen. An unmatched opted-in player receives solo waves while remaining eligible for matchmaking; solo waves use normal combat and defeat rules, but award half the normal XP. A newly formed realm replaces the active solo wave with a fresh competitive wave at the selected wave.
- The indexed SQL level column supports hero lookup by level. Live realm discovery intersects those durable hero records with the server's in-memory connected and opted-in set, then starts with the highest-level waiting player and chooses one to three lower-level opponents whose combined level is closest. Ties prefer fewer opponents, longer wait, then username; no level gap is rejected.
- A 1v1 is reciprocal. In 1v2/1v3 every team member attacks the solo player and the solo player's outgoing sends rotate across the team.
- Realm Guard identifies outbound recipients and Realm Attacker identifies inbound senders. The HUD shows their names, levels, down state, and queued items.
- Sending consumes exact equipment and queues it FIFO for future regular creeps. In the lobby or unmatched solo play, the player is shown as their own Realm Guard and Realm Attacker and sends into their own carrier queue. Carrier slots are allocated round-robin across attackers, overflow persists, and each player may retain at most 1,000 active or backlash queue entries.
- A regular creep that has another player's sent item equipped shows that player's username above the creep. Merely carrying a sent item without equipping it does not show the username.
- Closing a realm reverses undelivered items into hostile backlash queues against their original senders. Backlash pauses in Training Grounds and grants no realm-kill XP.
- A non-Training defeat immediately exits the defeated player from the active realm and returns them to a fresh wave-1 Training Grounds session in the Halls of Realms. It resets XP, level, base attributes, and the authoritative wave number to 1, retains inventory, removes half of Gold rounded down, and removes at most one Soul without allowing the balance below zero. When an opposing player's sent carrier dealt the killing blow, that carrier's owner receives the removed Gold and exactly one Soul even when the defeated player held none; neutral, backlash, and voluntary defeats simply destroy the victim's one-Soul loss. Every member of the active realm receives a chat-log system announcement naming the defeated player; an attributable player kill also names the killer and states that the killer gained one Soul. A lethal sent carrier grants no XP; enemy XP never derives from another player's level. Neutral and backlash lethals grant no realm-kill bonus. Before a combat death resets the build, the server queues a hostile echo with that hero's exact level, base stats, main hand, offhand, amulet, and charm for the highest-level hero on the server when that hero is someone else; ties use leaderboard order. The echo joins that recipient's next eligible wave. The highest-ranked hero's own deaths do not create echoes for a lower-ranked hero.
- Leave to Lobby is available after the final planned spawn and before the next global dispatch. Training Grounds repeat the current neutral wave without advancing it, halve enemy movement speed, clamp the hero to at least 1 HP, grant no combat rewards or drops, and allow all inventory management including sends into the player's own future carriers.
- Enter Realm is available at any time. Training continues until matching succeeds, then a fresh competitive wave starts with the normal preparation delay.
- The former tower-building and creep-purchase economy is removed from the active UI and protocol.
- Gold is granted occasionally and directly for defeated enemies according to `specs/PROGRESSION_SPEC.md`, and through manual item sales. Passive income and purchasing are not part of this slice.
- Neutral, competitive, backlash, and training waves are always supplied by the server.

## 7. Visual and UX Direction

- Mobile and coarse-pointer layouts keep the real CSS viewport and never scale the complete HUD, so the bottom-centered login and both viewport-edge header controls remain visible without desktop-site mode.

- HUD alignment refinement: the character and inventory overlays sit 12px from their respective side edges and 12px above the bottom; the spell rail, chat, and resource dock use the same 12px bottom anchor, with a further 12px separation from an open panel.

- `All` is selected when no graphics preference exists. The selected valid Lights mode is stored in browser local storage rather than player state and restored whenever a new scene initializes.
- Active hero status and beneficial-effect badges sit above the Health bar rather than above the central level badge. Every timed effect shows its rounded remaining time as a small suffix on the edge of its icon; values through `99s` stay in seconds, while longer values use compact minutes and seconds such as `1m40s`. Effects without a remaining time show no suffix. Every badge remains stable while hovered or keyboard-focused and exposes a tooltip naming the effect and its relevant live magnitude or mechanic, such as combined damage per second for damaging statuses or Reflective Surge's doubled returned damage and block-chance bonus; tooltips do not repeat the remaining time. The XP Send bonus uses a purple badge with its multiplier as the main label and the same small edge countdown suffix.

- A creep inspection character panel is intentionally compact: it shows only the creep name, level, live/current HP against combat maximum HP, current timed states, unmodified base attributes, and equipped Main hand, Offhand, Amulet, and Charm details. It does not show XP reward or the derived Effective stats section. Local and public hero character panels retain their existing advanced-stat presentation.
- Pointer-hover creep preview never replaces or expands the character panel. It appears as a compact, non-interactive tooltip centered at the top of the arena and shows only name, level, live/current HP against combat maximum HP, current timed states, equipped-item icons, and unmodified base attributes. Poison, Burn, Bleed, Frost/Freeze, Stun, Shock, Curse, Rapid Regeneration, and Reflective Surge use compact state badges, including stack count and the shared edge countdown suffix when applicable. Leaving the creep hides the tooltip and preserves whichever hero or committed creep inspection was already shown in the character panel.

- Use futuristic, simple geometric shapes with no required external art pipeline.
- Telegraph and combat rendering rules follow `specs/MECHANICS_SPEC.md`.
- Show controls, drops, and inspected enemy highlight. Every local or public hero profile header shows that hero's lifetime best wave beside their level. Selecting a creep replaces the character column with its inspection details, shows its live combat maximum HP after enemy-level and sent-item scaling rather than its unscaled derived build HP, and shows the XP that defeating that creep is currently worth after mode and balance reward modifiers; Training Grounds therefore show 0 XP. While in Training Grounds, `[Training Grounds - No Rewards]` remains visible immediately above the central level/XP circle. Moving over an active creep temporarily peeks the same inspection details without changing the committed selection, and moving away from all creeps restores the previously selected creep, hero, or local character sheet. Guard and attacker names in the realm header are clickable and replace the same character column with that hero's public stats and equipment; the same Back to hero button restores the local hero. The current first-ranked Souls leaderboard hero has a warning icon before their name everywhere realm membership is shown; its hover/focus tooltip explains that all other heroes' death echoes are sent into that hero's realm to fight.
- Show movement and auto-attack guidance as a centered, non-blocking notification that fades after a few seconds.
- A newly created hero sees a one-time multiplayer lore modal centered in the viewport above every other HUD surface and a full-page dimmed mask. Clicking either the mask or `Got it` dismisses the introduction. Its FTUE lore frames survival as the continuity of the hero's bloodline: Training Grounds prevent defeat and provide no rewards, while Enter Realm is the real test, provides rewards, and can match the hero against other players who are online. After a real defeat in a realm, the fallen hero's child takes over. This succession explains why XP, level, base attributes, and wave progress reset while inherited equipment remains and half of Gold plus at most one Soul is lost; a player killer always gains one Soul. It explicitly teaches that, while in a realm, the player can use an inventory item's `Send` button to invade another player's realm by arming a named creep in one of that player's future waves. In Training Grounds or unmatched solo play, the same action instead queues the item for the player's own future carrier, consistent with the realm rules. Dismissal is durable, and existing heroes created before this trigger was introduced do not receive it retroactively.
- Wave starts do not show a banner or routine notification; the fixed header's current-wave value is the persistent indication. Each dispatched wave is announced in the chat log as yellow system text containing its wave number and mode. When a competitive realm forms, yellow system messages announce every participant joining the realm to every member.
- Joining never pauses play behind a first-wave confirmation modal.
- The fixed header remains visible before login, spans the full viewport width, and shows the current `N players online` presence count. Its dark surface is semi-transparent and uses a CSS backdrop blur so the arena remains subtly visible beneath it, while its controls retain their existing 16px viewport-edge alignment. Before login and in every Training Grounds, waiting, and competitive realm state, its actions include `Devlog` and `Options`: Devlog uses the same ordinary header-button styling as Options, remains visible at every viewport width, and opens the in-game Devlog panel at the `/devlog` SPA route, while Options opens the same closable graphics-options modal used in the game. Browser Back closes the Devlog and restores `/` without reloading or disconnecting the game. Devlog no longer appears inside the Options modal. All ordinary header links and buttons share the same slightly rounded control shape and shadow-based hover/press feedback without positional displacement.
- The login panel is horizontally centered and bottom-aligned with a 16px gap from the viewport bottom. Submitting a username opens a password modal. A new username and an existing legacy account without a password both use the same create-password modal, including password confirmation, and the server durably stores the new password as a cryptographic hash on the account before accepting another command from that socket. Later username logins must show the password-login modal and verify that established hash rather than offering password creation again. Authentication feedback such as `Incorrect password.` appears inside the open password modal rather than behind it in the login panel. Incorrect passwords do not establish a session. A valid saved opaque hero id may still reconnect from that browser without prompting for the password. Successful account login or account creation opens the Characters view by default while the hero is in Training Grounds.
- The 3D canvas fills 100% of the viewport width and height. The compact game-information row, character panel, inventory panel, and all other stable HTML HUD surfaces float above it without resizing, offsetting, or pushing the canvas inward.
- The game page suppresses the browser context menu across both the canvas and every HTML HUD surface so right-button camera interaction never opens a native menu.
- While queued or inside a realm, the header includes one Swarm-mode toggle button. Normal mode reads `Release the warm!`; clicking it enables Swarm mode. Every transition from Training Grounds into a newly started waiting or active realm resets Swarm mode to normal/off. While Swarm mode is active, the same button shows the rounded-up seconds until the next wave and may be clicked again to return to normal mode. Swarm mode automatically requests a forced wave whenever its cooldown is ready and fewer than 100 enemies are active in the arena, waiting for the server result before another request. An accepted request immediately spawns every enemy still pending in the client's current wave queue in one shot, advances that player to the next wave, and dispatches the new wave without waiting for the global wave timer. The server authoritatively limits forced waves to one activation every `clamp(currentWaveNumber, 10, 60)` seconds. Hovering or focusing the toggle shows a tooltip explaining the automatic release, enemy-count threshold, and next-wave behavior. Training Grounds do not show the toggle.
- A single-row, borderless realm summary sits at the extreme left of the game-information header while queued or inside a realm. Options, the Swarm-mode toggle, and Leave to Lobby come first at that edge, with leaving disabled and gray until the server permits it; the `Wave N · Waiting for realm` or `Wave N` text sits immediately to their right. Guard, Attacker, and queue counts are omitted from this header. The centered presence summary combines the total count with current realm membership. A queued player without opponents sees `N players online - playing alone for now`. Once matched, it reads like `165 players online - Bob, Tyler and you in this Realm`: each other participant appears by clickable red username, `you` is italicized and non-interactive, duplicate memberships are shown once, and the names precede `you`. Training Grounds never show the former centered Halls of Realms modal. Their game-status bar instead contains red `Enter wave N` and `Enter wave 1` controls plus ordinarily styled `Devlog`, `Options`, `Characters`, and `Logout` controls: N is the hero's persisted best wave, each Enter control starts realm matchmaking at its stated wave, Devlog opens the routed in-game panel, Options opens the closable graphics-options modal over a full-page dimmed mask, Characters is available only in Training Grounds, and Logout ends the current session. The Characters control opens a modal that fills all space between the currently open Character and Inventory panels. It lists every account character, previews a hovered character in the existing Character panel in place of the active hero, and restores the active hero when the pointer leaves. Its bottom actions contain a large `Switch to <name>` button for the selected character beside a `Create new` button and new-character name input. There is no Kill Player header action. When the current hero is highest-ranked, the same death-echo warning shown beside realm names also appears beside that hero's name in the character panel.
- The options modal has an `X` close control. Its first setting is a `Fullscreen on game start` radio group with `On` and `Off`; On is the default, and the selected value is stored in browser local storage rather than player state. Its second setting is a `Resolution scale` range from 0.2 through 1.0 in 0.1 steps, defaults to 1.0, displays the selected percentage, applies immediately, and is also stored in browser local storage. Resolution scale changes only the canvas backing resolution: the canvas and game remain stretched across 100% of the page viewport, while backing width and height range from 20% through 100% of the device-pixel-ratio-adjusted dimensions. A Lights radio group displays `Off`, `Hero only`, and `All`. Off retains only a brighter ambient light so the scene remains readable. Hero only uses the hero's authored light plus a mild ambient light. All uses every authored global, hero, enemy, projectile, spell, and effect light while retaining ambient illumination at only about 5% so unlit shapes remain barely readable. Each mode recursively applies to every local light already in or subsequently added to the scene. A Shadows radio group displays `Off` and `Dynamic`, with Off selected by default and stored in browser local storage. The entire Shadows group is disabled while Lights is Off and restores its retained selection when lighting is re-enabled. Shadow Off disables the renderer shadow map. Dynamic enables percentage-closer-filtered shadow mapping, makes eligible scene meshes cast and receive shadows, and enables shadow casting for active directional, spot, and point lights, including objects and lights added later. Explicit presentation exclusions override that global mode: spell projectiles, Gold, and Scrap neither cast nor receive shadows, while the arena floor receives shadows but never casts them. A separate Devlog section opens `/devlog.html` in a new browser tab. The page renders a GitHub-style calendar grid of every generated ISO calendar week, running Monday through Sunday; selecting a week reveals its gamer-facing summary and every individually reportable source commit title. Generated history is kept in the tracked `changelogs/` folder with one `YYYY-Www.json` file per generated week. Coding LLMs should _NOT_ run `bun run changelog` commands themselves. Changelogs regenerates every week from the repository's first commit through the current week from scratch. A week with no commits is stored as the JSON string `No updates.` and has no generated summary. An initialization week whose only reportable entry is the synthetic `Initialized project` record is generated deterministically without Ollama. Every other non-empty week invokes local Ollama exactly once with `gemma4:latest`, validating each response before continuing so malformed or omitted periods cannot invalidate another week. A failed model call, parse, schema validation, or expected-week check stops generation with an error naming the week, model, and reason; there is no smaller-model fallback chain. Each strict JSON response supplies a gamer-facing summary for its requested week when that week contains updates, and the command writes the website-ready weekly files. Semantic `balance`, `fix`, `feat`, `ux`, and `perf` commits are individually reportable and respectively describe balance changes, fixed bugs, added features, design or experience changes, and the system whose performance improved. Graphical and rendering work may instead be summarized in the dedicated `graphics` bucket. `docs`, `chore`, `test`, and `refactor` commits never appear individually or create Devlog tags. The repository commit-message hook accepts those nine lowercase verbs in either `verb: description` or `verb(subject): description` form, where subject is a non-empty string naming the affected part.
- The Devlog page places its title, explanatory subtitle, and divider in that order as a top-aligned stack, then rotates the complete stack 90 degrees counterclockwise into a narrow left-side banner so its text reads when the viewer tilts their head left. The rotated banner begins at the same top edge as the change-history and community-request surfaces. On desktop, generated changelog history is the left content column and community requests are the right content column; both columns fill the 100vh viewport and scroll vertically within themselves rather than scrolling the whole page. Each period places its source-commit list beneath its gamer-facing summary in a collapsed-by-default disclosure labeled with the source-commit count. At viewport widths of 980 CSS pixels or less, the left-side banner is hidden, the content uses the full viewport width, and the content columns collapse into changelog-then-requests order. The request column shows the sorted future-month queue before the public feature, bug, or balance request form so visitors can review existing entries before submitting another. Balance requests report mechanics that players consider unbalanced. A Devlog search field appears above that form with an 18px gap above and below it. It filters the visible request queue immediately by case-insensitive title and description text while preserving its month groups and score ordering. The same query filters changelog history across every generated week by feature-summary text and source-commit title or description: nonmatching calendar weeks are hidden, the latest matching week is selected when necessary, and the selected week shows only matching feature lines and commits with matching commit disclosures expanded. Each column shows a dedicated no-results message when it has no match. A submission requires a type, a short title, and a description; submitting a new request or casting, changing, or removing a vote requires a currently active logged-in account, identified by the browser's saved hero id and verified against a live authenticated game socket by the server. Logged-out visitors may still read the complete Devlog and request queue. The form and vote controls remain visible but disabled without an active account and explain that login is required. A bug submission also records the browser name and version, operating system, full screen resolution in physical pixels, and device pixel ratio supplied by the browser; the server appends this environment block to the stored public description. The server validates and stores submissions in the shared SQL database and assigns them to the next UTC calendar month as candidates for future work. All visitors can see these future-month requests, ordered by net vote score and then creation time. Each account may hold one upvote or one downvote per request; choosing the opposite direction replaces the prior vote, and choosing the active direction again removes it. The API returns aggregate upvote, downvote, and net score counts without exposing account ids.
- The Devlog is a full-viewport panel inside the game application rather than a separate document; this routed panel supersedes the older separate `/devlog.html` page and new-tab wording above. Its surfaces are about 70% opaque and apply a light backdrop blur so the running game remains visible beneath them without compromising text readability. Its close control, browser Back, and the exposed mask on either side of the centered Devlog content close the panel through SPA history, preserve query parameters, and keep the live game socket mounted; clicks within the Devlog content do not close it. Direct navigation to `/devlog` opens the same panel. The request list, submissions, and votes use the HTTP origin derived from the same endpoint selection as the game WebSocket; therefore a local client opened with `?prod` reads and mutates production requests. The production API permits that cross-origin local-development access. While the player is waiting for or participating in a realm, attempting to close or reload the browser tab, follow an external navigation, or otherwise leave the app triggers the browser's native unsaved-changes confirmation. Internal SPA navigation does not trigger it.
- Every account has a durable `isModerator` flag that defaults to false. A currently connected moderator sees a Delete action on every community feature, bug, or balance request and may permanently remove requests that are completed or refused. The action sits at the right edge of the request card's first metadata row, opposite the request type and date. The request API verifies both the live authenticated socket and the server-owned moderator flag before deletion; ordinary accounts and disconnected moderator identities cannot delete requests. Associated votes are removed with the request.
- A newly created hero begins with the Character, Inventory, and Available Spells panels open so the starter build and choices are immediately visible. Clicking Enter Realm collapses the Character and Inventory panels if open and closes the Available Spells panel before matchmaking begins. Returning from a realm to the Halls of Realms, whether by Leave to Lobby or defeat, opens the Character and Inventory panels again while leaving the Available Spells panel closed. Reconnecting an existing hero retains the ordinary persisted onboarding-trigger behavior rather than forcibly reopening all three panels.
- Routine notifications appear inside the fixed header at its top-right edge instead of overlaying the arena or floating panels.
- Training kills do not create a transient no-reward notification because the persistent `[Training Grounds - No Rewards]` banner already communicates that rule.
- The health and mana displays sit directly beside the centered experience/level badge rather than stretching toward the arena edges. When either resource decreases, its colored fill updates immediately while a white recent-loss segment holds the previous value. Repeated losses debounce that segment's catch-up; after a short pause it animates down to the current value in the familiar fighting-game damage-bar style. Resource gains synchronize the segment immediately.
- Cooldown spells use one compact Ubuntu-dock-like vertical Spells rail on the left edge, anchored above the bottom-left health display. It shows only the six equipped active spells, shared regardless of whether each spell is learned permanently or granted by equipment, ordered by shortcut with `1` at the bottom and `6` at the top. Each badge centers its shortcut near the top inside a translucent, resource-colored circle; manual slots show their assigned key number, while auto-fire slots show a small dot instead of that number. The centered spell acronym and its current effective level share one vertically aligned line formatted like `HE lv12`, with a space before the smaller 8px white level label and no maximum-level suffix; auto-fire also retains its four gold corner triangles. The rail uses the same slight corner rounding at its top and bottom. A small `...` control beside the rail, or `K`, opens the Available Spells modal. The modal is vertically scrollable and shows every authored spell, dark and desaturated while unavailable, grouped and sorted by its payment resource in HP, Rage, then Mana order. Every entry shows its authored description, resource, active/passive type, current available level when acquired, and its separate maximum permanently learned level from extraction; temporary equipment levels never inflate that learned value. Hovering or focusing an acquired active spell then pressing `1` through `6` assigns it to that exact loadout slot, replacing the prior occupant. Passive spells are visible in the catalog but never occupy a shortcut slot. The rail and modal are the complete activation surface: a spell outside the equipped rail never triggers.
- The spell modal interaction supersedes its earlier number-key assignment wording: it shows six numbered destination slots at the top; tapping or clicking an acquired active spell selects it, then tapping or clicking a destination assigns and replaces that slot. The catalog preserves scroll position across continuous combat updates and supports wheel, touch-pan, scrollbar, and keyboard scrolling. Its additive checkbox buttons control learned, equipped, active, passive, and unavailable visibility as defined below. Gameplay number keys continue to cast their assigned spells.
- The Spells rail places every available passive above the six active loadout badges. Passive and active badges share the same full size; passives show their effective level and tooltip, remain visibly resource-colored or dark when non-operational, and have no shortcut, auto-fire marker, or equip interaction because availability activates them automatically. The rail expands to its contents and has no scrollbar or internal scrolling.
- The spell catalog keeps its word-search field and uses five checkbox buttons in two visibly separated flex groups: the status group contains Learned, Equipped, and Unavailable, while the type group contains Actives and Passives. Opening the modal resets the selection to Learned, Equipped, and Actives. Learned includes spells whose permanent extracted level is positive; Equipped includes spells supplied by currently equipped items; Unavailable includes spells that are neither learned nor supplied by equipped items; Actives includes authored non-passive spells; and Passives includes authored passive spells. Selections are ORed within each group and ANDed between groups, with a group imposing no constraint when none of its buttons are selected. A card must also match the word search, and empty resource sections hide. Spells have no minimum hero-level requirements.
- Use a 320px independently scrolling character/stat panel and a 640px equipment panel as floating canvas overlays. The character panel sits against the left screen edge and the inventory panel against the right, both clearing the 52px header with 12px of breathing room and ending flush with the viewport bottom. Both open side panels use CSS backdrop blur and are ten percentage points more transparent than their prior surfaces: character uses `rgba(13, 20, 24, 0.72)` and inventory uses `rgba(13, 20, 24, 0.8)`. When either panel expands, it fades and slides inward from its own side without perspective or rotation; both open panels settle at `translateX(0)`. The panel containers retain `will-change: transform, opacity` to keep the transition smooth, and reduced-motion preferences suppress the entry movement. Opening the character panel shifts the bottom-left spell rail right so its left edge sits 12px beyond the panel; closing the panel returns the rail to its 14px viewport inset. Opening inventory similarly shifts chat left so its right edge sits 12px beyond the panel; closing inventory returns chat to its 16px viewport inset. The lower spell rail, chat, resource dock, and both panels share a zero-pixel viewport-bottom anchor now that panel toggles no longer occupy those corners. The header, notifications, centered toast, multiplayer introduction, and player level badge remain viewport-anchored as panels open or close. Closing a panel hides its entire surface and contents without shrinking it into a visible empty column; it has no closed border, background, blur, shadow, or input interception. Each panel has its own icon toggle in the fixed header: Character at the left edge and Inventory at the right edge. They open or close independently; `C` toggles the character panel, while either `I` or `V` toggles inventory when keyboard focus is not in an editable control. Its currencies and equipment count remain fixed at the top, its filters remain pinned to the bottom even when few items are present, and only the equipment list between them scrolls. Committing a creep selection forces the character panel open and replaces its contents with that creep; clearing the selection restores the local hero and the panel's exact pre-selection open/closed state. Temporary pointer inspection does not change that saved state.
- Canvas backing dimensions follow the full-viewport canvas element at the selected browser-local resolution scale. Panel collapse/expand transitions never change the CSS viewport dimensions; viewport and camera sizing still observe the canvas element rather than depending only on browser-window resize events.
- Keep essential arena HUD elements readable when the floating build panels overlap the canvas.
- On touch-capable devices, a one-finger drag on unobstructed canvas space controls camera yaw and pitch with the same bounds and inverted local-X behavior as right-mouse dragging. A compact virtual movement stick appears near the lower-left arena edge and supplies camera-relative analog movement without blocking HUD controls. Touch-oriented viewports at 900 CSS pixels wide or less render the HTML HUD at 72% scale so it occupies less of the mobile play area while the 3D canvas remains full-viewport.
- Player-facing floating-point values use at most two digits after the decimal point across HUD sheets, spell tooltips, costs, and item details; authoritative calculations retain full precision.

- The former Devlog section inside Graphics Options is removed; Devlog navigation is owned exclusively by the fixed header under the visibility rules above.

## 8. Architecture

The codebase is a modular monolith with shared, environment-independent game-domain modules. Browser, canvas, WebSocket, HTTP, and process APIs stay at composition boundaries; progression, content generation, balance, wave construction, inventory transactions, and combat calculations remain pure and directly testable. Randomness, clocks, and identifiers are injected wherever outcomes affect game state.

Every combat actor is a `Unit`, including the local hero, regular enemies, champions, invaders, clones, and bosses. A unit owns build inputs, mutable resources, retained timed effects, and one authoritative compiled `UnitState`. `UnitState` is rebuilt from clean defaults at the beginning of every fixed update, applies equipped items in Main hand, Offhand, Amulet, then Charm order, and then applies passive, aura, buff, debuff, and status effects in ascending authored priority and application order. It contains the complete effective offensive, defensive, utility, resource, movement, reward, and status-related values consumed by simulation and presentation. Runtime systems and the HUD do not independently reconstruct those values.

Effects use one shared plugin contract. Each effect owns its priority, whether it participates in stat previews, its handler, lifetime, and stack/refresh/replace/reject policy. Handlers receive the current unit-state draft, the fixed sorted effect snapshot, and elapsed time; they may mutate the draft or call unit resource/effect methods. Effects added while a snapshot is compiling are retained but cannot run until the following fixed update. Equal priorities preserve application order. Concrete effect types use explicit priorities rather than priorities assigned from runtime discovery order.

HUD projections use the same compiler on a detached target. Equipment replacements and upgrades, attribute allocation, extraction, passive previews, and hypothetical active buffs are expressed as projected addons. Projection executes only effects marked as stat-relevant with a one-second preview delta, returns a separate projected state, and discards every resource, timer, damage, and effect-list mutation made to the detached target. A live unit never stores projected state.

Stable HTML HUD structures are created once. The fixed simulation loop may update scalar text, style, and ARIA properties, but it does not replace panel, resource, realm, spell, inventory, or form subtrees unless a flattened render signature for that subtree changes. Inventory changes reconcile keyed equipment cards in place: unchanged cards and the scroll container retain their DOM identity, changed cards update at their ordered position, and adding, removing, equipping, or changing a stack quantity never resets the equipment list's scroll position. Resource updates revalidate resource-gated inventory actions; an equipment card's signature changes only when the resulting action availability changes, not for every balance change. Canvas owns arena action rendering; HTML remains the accessibility and interaction surface for forms, inventory actions, and persistent stats.

Inventory equipment cards reserve a compact fixed-width action column so item names, requirements, effects, and combat values remain readable inside each column of the 640px, two-column inventory drawer. Sell, Purge, Upgrade, Send, and Extract buttons use concise labels and remain full-width only within that narrow action column.

### Client

- `src/game/Game.ts`: thin browser composition root and fixed-step loop.
- `src/game/ArenaState.ts` and `src/game/systems/`: local arena state plus focused movement, combat, collision, spawning, loot, defeat, and cleanup systems. Systems emit arena events and do not access WebSockets or DOM nodes.
- `src/game/GameObject.ts`: abstract update/render base.
- `src/game/Unit.ts`: health and velocity-based steering shared by hero and creeps.
- `src/game/Hero.ts`: WASD-controlled hero, resources, closest-target auto-aim, and equipped-weapon state.
- `src/game/Creep.ts`: melee and bubble-shooter steering and attack state machines.
- `src/game/AttackArea.ts`: telegraphed, dodgeable melee weapon attack areas.
- `src/game/Projectile.ts`: moving collision-based enemy bubbles.
- `src/game/Map.ts`: fixed arena dimensions, bounds, edge spawning, and arena rendering.
- `src/ui/`: stable DOM views driven by presentation models rather than simulation objects.
- `src/ui/HeroResourceDock.tsx`: stable hero Health, Rage, level/XP, Mana, timed-effect, Training-state, and XP-toast presentation; `Hud.tsx` supplies projected regeneration values and the current player snapshot.
- `src/net/SocketClient.ts`: validated WebSocket transport. Session storage is a separate browser adapter.
- Local storage persists only the accepted opaque hero id and username for reconnect convenience, never authoritative progression or transient combat state. Logout erases that reference.

- `common/protocol.ts`: runtime-validated protocol messages and shared types.
- `common/balance.ts`: the single authoritative wave, combat, and reward balance configuration used in every environment.
- Shared progression, inventory, content, combat, item, and wave rules live in `common/` and have no browser or server runtime dependencies.

## 9. WebSocket Protocol

Client to server:

- `join`: exactly one of `{ name, password?, passwordConfirmation? }` or `{ heroId }`. Sending an account name without a password performs no login and returns `authenticationRequired` with mode `create` for a new or legacy passwordless account, or mode `login` for a password-protected account. Sending an account name and password creates the account and its first same-named character, sets a legacy account's first password, or verifies an existing hash before login. New-password submission includes a matching confirmation, and passwords contain 8-128 characters. An opaque character id reconnects a saved browser. Login is rejected while any character on that account owns a responsive active socket.
- `createCharacter`: `{ name }`; available only on an authenticated socket, creates a fresh character on that account, switches the socket to it, and rejects names already used by any character. `switchCharacter`: `{ heroId }`; switches only to another character owned by the authenticated account. Both operations leave the current realm and preserve the account's shared stash. Every `welcome` includes the account's character summaries so the HUD can create or switch characters without logging out.
- `logout`: `{}`; releases the active hero immediately, performs normal realm cleanup, clears that hero's transient arena and queue state, and leaves the socket anonymous.
- `listHeroes`: `{}`; available before login and returns the public leaderboard.
- `inspectHero`: `{ heroId }`; available before login and returns the public build projection for one hero.
- `dismissPanelTrigger`: `{ panel: "character" | "inventory" | "multiplayer" }`; durably consumes that hero's pending one-time panel auto-open trigger or multiplayer introduction.
- `updateAllocation`: `{ allocation: { agility, strength, spirit, intelligence } }`
- `respecStats`: `{ allocation: { agility, strength, spirit, intelligence } }`; charges `100 * currentLevel`, saves the supplied valid five-point allocation, and reapplies it retroactively to every earned level.
- `creepDefeated`: `{ unitId }`
- `collectDrop`: `{ dropId }`
- `reconcileDrops`: `{ activeDropIds, pendingDropIds }`; reports the client's current arena-drop view so transiently lost pickup requests and orphaned Gold, Scrap, or equipment can be repaired.
- `deferDrop`: `{ dropId }`; validates an owned equipment drop pushed beyond the arena and returns it to the same player next wave.
- `equipItem`: `{ tileId }`
- `sellItem`, `purgeItem`, `upgradeItem`, `sendItem`, `extractSkill`: `{ tileId, bulk? }`; `bulk: true` is authored by Shift+click and repeats the selected action server-side until it can no longer make progress.
- `setRarityAction`: `{ rarity, action }`; changes the auto-action preference for a rarity tier. `action` is one of `"keep"`, `"auto-sell"`, `"auto-purge"`, or `"auto-send"`. The server persists the choice in `progress.rarityActions` and applies it to future item collections.
- `setSkillEquipped`: `{ skillId, equipped }`; adds or removes one available active spell from the persisted spell loadout. At most six active spells may be equipped; the server rejects unavailable skills, passive skills, and additions beyond the limit.
- `toggleSkillAutoFire`: `{ skillId }`; toggles automatic firing for an equipped active spell. Auto-fire is cleared when that spell is unequipped.
- `heroDefeated`: `{ sourceUnitId? }`
- `requestWave`: `{}`
- `scoreSnapshot`: `{ score, health }` (reserved for future validation)
- `leaveRealm`: `{}`
- `enterRealm`: `{ waveNumber }`; the server accepts only wave 1 or the hero's current persisted best wave (minimum 1).
- `forceNextWave`: `{}`; outside Training Grounds, the server accepts it only after the player's wave-scaled cooldown, advances that player by one wave, and replies with `forceNextWaveResult` before dispatching the new `incomingWave`. The result includes whether the action was accepted and the authoritative epoch-millisecond ready time; only an accepted result causes the client to spawn its complete pending current-wave queue immediately.
- `chat`: `{ text }`; always rebroadcasts the text message to the sender. When the sender is currently in a realm, the server also sends it to every other realm member.

Server to client:

- `forceNextWaveResult`: `{ accepted, readyAt }`; reports whether the force request advanced the wave and the authoritative epoch-millisecond time when the action becomes available again.
- `welcome`: `{ playerId, player, progress, realm, config }`
- `loggedOut`: `{}`
- `authenticationRequired`: `{ username, mode }`, where mode is `create` or `login`.
- `leaderboard`: `{ heroes, onlineCount }`; `heroes` contains at most the top 100 players ordered by currently held Souls descending and username ascending, while `onlineCount` counts every connected player even outside that displayed top 100. Each entry contains `{ id, username, level, souls, connected, receivesDeathEchoes }`. Connected heroes use a filled teal row in the anonymous hero list, while offline heroes use a transparent teal outline with high-contrast text so their names, levels, and Souls remain readable. The death-echo flag is true only for the first-ranked hero.
- `heroProfile`: `{ hero }`; the public hero projection contains id, username, level, attributes, equipped items, and learned/equipped skill state, but excludes currencies and backpack contents.
- `realmUpdated`: `{ realm }`
- `incomingWave`: `{ wave }`; `wave.resetHero` is true only when entering a newly requested solo realm or newly matched competitive realm, and false for ordinary dispatches within the current realm.
- `creepDefeatResolved`: `{ unitId, score, progress, drops, reason }`
- `collectItemResult`: `{ dropId, collected, reason }`
- `dropsReconciled`: `{ drops, removeDropIds, resolvedDropIds }`; returns every server-ledger drop missing from the client, identifies client-only drops to remove, and releases pending pickup ids whose outcome can no longer arrive.
- `progressionUpdated`: `{ progress, reason }`
- `waveAdjusted`: `{ waveNumber, reason }`
- `scoreAwarded`: `{ score, reason }`
- `serverNotice`: `{ message, tone }`, where `tone` is `success` or `error`; authentication responses use this explicit result tone so the open password modal can distinguish green progress/success feedback from red failures.
- `chatMessage`: `{ senderId, senderName, text, kind? }`; sent to all members of a realm when one member sends a chat. Also used by the server at wave dispatch to notify a player that another player's sent creeps arrived in their realm; these notices retain the opposing sender id so the name is red. `kind: "system"` omits the sender prefix and renders the text in yellow for wave, realm-join, and death announcements. Ordinary chat displays `senderName: text` with the name in green when the sender is on the same side (both guard or both attacker) and in red when they are an opponent.
- `groundDropCreated`: `{ drop }`, where `drop` is a tagged `item`, `gold`, or `scrap` ground reward.

The server records units issued in each wave and accepts a unit defeat at most once. Unit records retain sent-item emitter attribution. XP, score, gold, and drops derive from that record. Generated and equipment-swap drops remain in a server ledger and are collected or deferred by opaque id. The client reconciles its active and pending opaque drop ids after connection recovery and whenever a pickup acknowledgement times out. The server's ledger is authoritative: client-only drops are removed, server-only drops are reissued, and pending ids absent from the ledger are released because they were already collected, retired with the arena, or otherwise resolved. Reissued drops appear at the hero's current position because drop positions are client-owned simulation state. Protocol payloads are runtime-validated; malformed or out-of-state commands do not mutate player state. Protocol compatibility is numeric version 42.

Bun SQL is the authoritative durable hero store. Each hero row stores its opaque character id, globally unique character name, indexed level, owning account id/name, password hash, moderator flag, and serialized character JSON. Existing rows migrate in place by treating their hero id/name as their account id/name. The password column contains only Bun password hashes; null marks a legacy account that must create a password on its next account-name login. The blob contains score, current and maximum wave numbers, XP, attributes, allocation, currencies, learned skills and levels, universal unlocks, disabled skill ids, equipped items, shared inventory stacks, and quantities; the indexed level always matches the blob's progression level. Account and character names allow 1–20 ASCII letters, digits, `_`, or `-` and preserve display casing. Account names and character names are each compared case-insensitively. Repository writes mark every sibling character dirty so their duplicated shared-stash snapshot remains identical and reload groups each account onto one in-memory inventory reference. With no `DATABASE_URL`, local development uses `sqlite://./server-data/players.sqlite`; when present, `DATABASE_URL` selects production and must be a `postgres://` or `postgresql://` connection. Existing JSON snapshots are not imported. Realm membership, matchmaking opt-in, issued units, ground drops, deferred items, incoming sends, backlash queues, and socket state exist only in memory.

## 10. Balance Profiles

- Local development and production use the same authoritative balance and progression configuration; there is no development balance variant. Public simulation modifiers are sent in `welcome`.
- Normal waves contain `min(40, 10 + 2 * max(0, waveNumber - 1))` regular enemies. Wave 1 therefore starts with 10 regular enemies. The raw count stops growing at 40 so long-running games scale through enemy strength rather than unbounded active entities.
- A normal regular enemy uses level `max(floor(heroLevel / regularCount), floor((waveNumber - 1) / 2))`. A normal golden rival uses the wave-authored level `max(1, floor((waveNumber - 1) / 2) + 1)`. The divisible-by-10 competitive clone event defined in `specs/PROGRESSION_SPEC.md` is the explicit exception: clone level and rewards divide the current defender's level across the opposing attackers.
- The normal profile retains the 60-second wave interval, three-second preparation delay, ten cumulative spawn batches five seconds apart, and rival spawn after 75% of regulars.
- Development never accelerates progression. The `dev` profile currently uses the same wave, combat, XP, gold, and drop values as `normal`; its separate id remains available for future diagnostics that do not alter player advancement.

## 14. Reimplementation Blueprint

This section records composition details that a clean-room implementation in another language must preserve in addition to the behavior in the other specification sections.

The current client intentionally uses the proven legacy Three.js WebGL renderer for the main scene because the WebGPU path can silently omit loaded GLB character materials. WebGPU remains deferred until those assets are compatible.

- The browser document contains one full-window application root, a canvas for all world action, and persistent DOM HUD panels. Three.js prefers its WebGPU backend, but falls back to the legacy WebGL renderer when WebGPU is unavailable, initialization fails, or a WebGPU render pipeline fails at runtime; the fallback keeps the game usable on browsers and drivers with incomplete WebGPU support. The client always opens `/ws` on the page's own host and port by default, using `ws` for an HTTP page and `wss` for HTTPS. A bare `?prod` shortcut connects to `wss://pvp.up.railway.app/ws`. A `?server=<baseurl>` query overrides both the page origin and `prod`; the legacy `?ip=<baseurl>` query is an equivalent fallback when `server` is absent and also takes precedence over `prod`. A bare authority such as `?server=pvp.up.railway:443` defaults to secure WebSockets, while an explicit `http`, `https`, `ws`, or `wss` URL selects its corresponding WebSocket scheme; local or LAN overrides that do not support TLS therefore use an explicit `ws://` URL. The client appends `/ws` to the override's optional base path unless that path already ends in `/ws`. Empty, malformed, credential-bearing, or unsupported-protocol overrides fall back to the page origin. After renderer initialization succeeds, the client starts a request-animation-frame renderer plus a fixed 60 Hz simulation accumulator. A rendered frame may contribute at most 100 ms to the accumulator to avoid an unbounded catch-up spiral. A one-second timeout watchdog checks the elapsed time since the last real animation-frame callback; when that callback has been stale for at least 750 ms, the watchdog advances and renders one frame through the same capped accumulator path. The watchdog never requests another animation frame and does not advance when normal animation frames are current, preventing both a background-tab spawn backlog and competing foreground loops.
- The world is 32 by 20 meters, represented internally by 1,600 by 1,000 logical canvas pixels at the shared presentation scale of 50 logical pixels per meter. Gameplay descriptions and HUD values use meters or meters per second; internal simulation and layout geometry may retain logical pixels. The camera viewport equals the canvas CSS content size and always centers on the hero. When the viewport is smaller than the arena the hero is kept at center as long as the arena edges remain visible; when the viewport is larger than the arena the map is centered on screen. Canvas backing width and height equal CSS dimensions multiplied by device pixel ratio and the selected resolution scale, without changing the CSS viewport size. Both window resize and `ResizeObserver` trigger this calculation.
- The client validates incoming envelopes before dispatch. Outgoing messages sent before the socket is open are discarded rather than buffered. On socket open, a locally stored opaque hero id may be submitted automatically. The local-storage key is `multi-line-tower.session` and contains only `{ heroId, username }`; invalid JSON, non-string values, or missing/empty fields are treated as no session. Unavailable browser storage is tolerated during load, save, and logout; logout attempts to clear the reference without interrupting the client.
- Joining by name trims the value, requires 1–20 ASCII letters, digits, `_`, or `-`, preserves its display casing, and compares it case-insensitively. Username login requires the account password; the first accepted use creates the hero and hashes its password, while a legacy passwordless account must establish a password before it can connect. A new hero starts with the specified starter loadout and progression defaults.
- The HTTP server serves the built `dist` directory when it exists (otherwise the repository root), maps `/` to `index.html`, uses explicit HTML/JavaScript/CSS/SVG content types, rejects normalized paths outside the public root with 403, and otherwise falls back to `index.html` for missing paths. The WebSocket server shares that HTTP listener and accepts connections only at `/ws`. It listens on LAN-reachable `0.0.0.0:3000` by default so the machine is available as `olim3.local`; `HOST`/`PORT` may override it. Every environment uses the same authoritative balance configuration.
- Each connection must join before gameplay commands. Anonymous sockets may request leaderboard summaries and public hero profiles. Invalid JSON or schema-invalid input receives `Ignored invalid message.`; other commands before identification receive `Join before playing.` Only one socket in the authoritative game-server process may own a hero. Logout or disconnect releases it immediately.
- The server runs WebSocket heartbeat checks using ping/pong. A socket without a pong or other valid inbound activity for five minutes is terminated and processed through normal disconnect cleanup. The five-minute application timeout is authoritative even when the WebSocket library or deployment platform has a different default.
- A single 60-second server timer drives global wave dispatch. At dispatch, every realm's down set is cleared; every connected realm member or opted-in solo increments their wave, while Training Grounds players repeat without incrementing; then every connected player receives the correct competitive, solo, or training wave.
- Durable hero changes remain authoritative in server memory and mark the affected player record dirty. The serialized profile includes the resettable current wave and monotonic maximum wave reached; public profile inspection displays that lifetime best. A separate one-minute write-behind timer snapshots and upserts only dirty players. SIGINT and SIGTERM begin one idempotent graceful shutdown: the server stops accepting new commands and connections, immediately sends WebSocket close code 1012 (service restart) to every client, drains already accepted per-socket command chains, performs and awaits a final dirty flush, closes SQL, force-terminates any socket that did not complete its close handshake, and closes HTTP before exiting successfully. Database flush and close therefore cannot be delayed by lingering sockets within the host's 10-second termination grace period. Gameplay commands, joins, and wave dispatch do not synchronously wait for database writes. A failed batch restores its dirty flags for a later retry and is logged; therefore an abrupt process or machine failure can lose at most the unflushed interval of progression.
- Startup creates `heroes(id TEXT PRIMARY KEY, username TEXT NOT NULL, level INTEGER NOT NULL, password_hash TEXT, hero TEXT NOT NULL)`, adds the nullable password column to existing tables, and creates a unique `lower(username)` index and level index through Bun SQL. Repository operations are asynchronous and serialize writes so older snapshots cannot overwrite newer state. SQL startup failures stop the server. The default local SQLite parent directory is created before connection. Production connection credentials are never logged.
- Runtime validation is intentionally asymmetric in this prototype: client commands receive full discriminated-union validation, while server messages are validated by their recognized `type` envelope and then treated as the matching typed payload. Protocol compatibility is numeric version 41 delivered in `welcome`.
- When logged out, the client keeps the fixed header visible and shows the join form at the bottom center. The top-100 hero leaderboard is a separate panel anchored to the left and vertically centered; it is limited to 90% of the viewport height and scrolls vertically within that height. The server pushes a fresh leaderboard to every socket whenever a hero joins, logs out, or loses their final socket, so the header's total online count and leaderboard styling reflect current in-process presence without a page refresh. Clicking a row renders the selected hero's attributes, effective stats, equipped items, and skill state read-only in the character panel; currencies, backpack contents, allocation controls, and actions remain hidden. Logout clears the saved reference, resets the local arena, and returns to this anonymous view without closing the socket.
- Newly created heroes use the open-panel contract above rather than the legacy delayed Character and Inventory panel triggers. Existing persisted heroes may retain those durable one-time trigger booleans for compatibility: automatic opening, explicit dismissal, or manually toggling the corresponding panel consumes its trigger so later progression never overrides the player's choice. These visibility changes do not alter or preview gameplay state.
- Stable-DOM performance is behavioral: scalar resource/XP values update in place each frame; expensive character, spell, realm, and inventory subtrees are replaced only when their flattened signatures change. Canvas owns map, units, telegraphs, projectiles, drops, spell effects, selection, indicators, and floating combat text; DOM owns joining and all persistent interactive controls.

## 13. Development Process

- New scenes restore a valid browser-local Lights preference and otherwise use the `All` default below.

- Lights default to `All` when no graphics setting has been selected, and every new scene initializes from that same shared default. `Off` disables lighting and renders every mesh with an unlit material so its authored color remains readable. This applies recursively to existing and subsequently added meshes and supersedes the earlier ambient-only Off description.
- SIGINT begins immediate graceful shutdown. Superseding the earlier immediate-SIGTERM description, SIGTERM for managed redeployments first broadcasts a realm system message to every joined player that the server will restart and disconnect them in 30 seconds, keeps the server available during that countdown, and then begins the same graceful shutdown. The deployment termination window must exceed 30 seconds; SIGKILL itself cannot be observed or delayed by an application.
- When the WebSocket closes, the client appends a system entry to the chat log stating that the server closed the connection, including the close code and server-supplied reason when available, while the reconnect notice remains visible.
- `bun run reset` transactionally deletes local heroes, checkpoints the SQLite write-ahead log, and verifies that zero heroes remain while preserving the schema.

- `specs/SPEC.md`, `specs/MECHANICS_SPEC.md`, and `specs/PROGRESSION_SPEC.md` are the source-of-truth specification set. Update the relevant spec before implementing behavior not already covered.
- Keep filenames, runtime choices, protocols, mechanics, progression rules, and UX synchronized with implementation.
- Use Bun for project scripts and tooling.
- `bun run release-check` fails when the working tree contains staged, unstaged, or untracked changes, then compares `HEAD` with the newest commit that touched `changelogs/`. A clean matching repository reports that new commits are not missing from the tracked changelogs; a mismatch fails the check.
- `bun run release-push` stages every change under `changelogs/`, commits it as `docs(automation): release changelog update`, and pushes the current branch. Any failed step stops the release push.
- Dependency installation configures the repository's commit hooks only in local development: the automatic prepare step skips CI and environments without a Git worktree. `bun run hooks:install` remains the explicit local command for installing the hooks.
- `bun run reset` deletes every hero from the local development SQLite database at `server-data/players.sqlite` while preserving its schema. Stop the local server before resetting so its in-memory players cannot be persisted back into the database. The reset command never uses `DATABASE_URL` and therefore cannot target production.
- `bun run features` fetches the public production `/api/devlog/requests` endpoint and prints every player-submitted feature request as formatted JSON, retaining the public queue's score ordering and aggregate vote counts while excluding bug and balance reports. An optional first argument overrides the API base URL for local or alternate deployments. The command uses only the existing read-only HTTP API and never opens a database connection or accepts database credentials.
- `bun run feature-agent <codex|claude|pi|opencode>` requires a clean Git worktree, fetches and randomly selects one pending feature through the same public API, displays the complete selection, scans its untrusted title and description for prompt-injection, secret-exfiltration, destructive-command, and encoded-payload indicators, and requires explicit interactive confirmation before starting the selected coding harness. The harness receives the selected request as delimited untrusted data, must treat it only as a product request, follows the repository spec-first workflow, validates its implementation, and commits the completed change without pushing it. Unsupported harnesses, an empty queue, a non-interactive terminal, a declined confirmation, or a missing harness executable stop before any AI task starts.
- Public feature, bug, and balance submissions use a 3-100 character title and a 10-1,024 character stored description. Bug environment metadata counts toward the description limit so no request exposed to automation can exceed 1,024 characters.
- Debug builds may expose `window.__mltDebug` and concise `[MLH][player]` logs for socket, wave, spawn, combat, defeat, and score events.
- The first generated devlog week represents repository creation as one reportable `Initialized project` entry, even when the root commit predates the semantic commit convention; it is never rendered as an empty week.
- Generated non-empty Devlog periods serialize `summaryTitle` and `summary` before `commits`. Every model response is schema-validated before use. `summary` is an object containing only the `features`, `bugfixes`, `performance`, `balance`, `ux`, and `graphics` buckets, each represented by an array of concise gamer-facing update lines. Every distinct player-facing feature and fixed problem receives coverage in `features` or `bugfixes`; related commits may be consolidated around a parent concept, but important standalone systems remain distinct and cannot be omitted. Performance, balance, UX, and graphics instead provide short, aggressively consolidated higher-level recaps. Updates appear in only their primary player-facing bucket without copied semantic commit prefixes. Before strict validation, the generator narrowly normalizes model drift by trimming and removing blank bucket entries, wrapping a non-empty bucket string as one line, moving only recognized bucket keys from the period into `summary`, and unwrapping a period whose sole key is one single-entry `periods` array; unknown keys and all other malformed shapes still fail. The Devlog renders each non-empty bucket as a distinct heading and bullet list, and derives its visible tags from those same non-empty buckets. Legacy generated string summaries remain readable until their weeks are regenerated: double newlines render as horizontal rules and single newlines render as line breaks.
